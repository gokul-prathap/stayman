# Delete confirmed test bookings and dependent records

This is a one-off SQL Editor operation, not a deployment migration. It does not run automatically. The supplied options select **Hostarica**, property UUID `10000000-0000-0000-0000-000000000001`. Verify that identity before using it.

1. Open `cleanup-test-bookings.sql`, copy the entire file into Supabase SQL Editor and Run with `execute_delete=false` (the default).
2. Review `guests`, `bookings`, per-table counts, conflicts, issued invoice records and identity-file paths. The rule matches the substring `test` anywhere in a name, case-insensitively, including names such as `Gokul Testing` and `test 2`; it is not an exact-name rule.
3. If `conflicts` is not empty, stop: a real/non-test group contact/member or shared guest/invitation may be affected. This script will refuse deletion of the entire selection rather than remove unrelated people.
4. If identity files are listed, remove exactly those paths from the `guest-identities` bucket using Supabase Storage dashboard/API before database deletion. Do not delete `storage.objects` directly; that does not properly remove file bytes. The script refuses deletion while those files remain.
5. Preserve an appropriate database backup before committing irreversible test-data deletion. Copy the reviewed `preview_token`. In the same SQL file set `execute_delete` to `true` and paste that token into `expected_preview_token`. If issued invoices appear, only set `allow_issued_test_invoices=true` after confirming every listed invoice is disposable test data, not real issued billing history. The script never resets invoice numbering sequences.
6. Run the entire edited file. If any dependent data changed, the token check fails and nothing is deleted; preview again. Any error rolls the transaction back. Do not remove constraints or guards to force it through.
7. Refresh Stayman's guest/reservation lists, reports and Aiosell diagnostics. With automatic updates enabled, check delivery of newly freed inventory and actual OTA availability. This database cleanup does not cancel a booking at an external OTA or issue a customer refund. If a real external reservation is found, use its normal cancellation/reconciliation process rather than deleting it here.

The script selects matching guest contacts, group-member names, linked check-in names and current name-correction records within the property. It removes related allocations, accommodation/folio payments (including legacy folio-only linkage), charges/folios, edits, guest corrections, relevant audit rows, invitations and Aiosell booking/event references. It uses UUID references in known audit JSON instead of blindly deleting every record containing the word test.

It preserves property settings, physical rooms/beds, unrelated guests/bookings, staff/auth accounts, global daily check-in counters, unrelated expenses/stock records and invoice sequences. It does not disable foreign keys or triggers. Unknown/new dependencies cause rollback rather than a partial cleanup. It does not claim to erase external provider history, backups, platform logs or unlinked arbitrary text copies of a name. Exact database matches and discovered storage paths define this cleanup's scope.
